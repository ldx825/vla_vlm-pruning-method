# AutoPrune 多视角剪枝组会报告（2026-03-31）

## 1. 报告目标

这份报告主要回答四个问题：

1. 我们针对原始 AutoPrune 新增了哪些算法设计。
2. 为什么此前在 VILA 上的实验没有得到理想结果。
3. 为什么迁移到 Mantis 之后，实验结果开始显著变好。
4. 当前最值得保留的实验结论是什么，下一步最应该优化什么。

本报告尽量用直白语言说明问题，少用缩写。确实需要提到英文名字时，只在第一次出现时保留完整名，后面尽量用中文解释。

## 2. 研究背景与核心目标

我们的任务不是普通多图问答，而是更强调“同一任务、多个观察视角”的多视角推理。  
因此，我们希望视觉剪枝方法同时满足三件事：

- 剪枝后模型效果尽量不掉。
- 剪枝后真实推理延迟能够下降。
- 算法本身具有解释性，并且以后能迁移到别的视觉语言模型、视觉语言动作模型上。

原始 AutoPrune 的主要优点，是能够在不同层逐步压缩视觉 token，而不是一上来一次性剪完。  
但随着实验推进，我们逐渐发现：

- 如果剪枝层数太固定，简单样本会被“过度执行”。
- 如果预算完全靠手调上下限，算法解释性会下降。
- 如果评测协议和模型形态不匹配，即使模型本体已经省下了计算，端到端结果也可能不明显。

因此，这轮工作的重点不只是“把代码跑通”，而是把算法、评测协议、实验结论三者同时理顺。

## 3. 新增算法一：剪枝层数自适应压缩

### 3.1 原始问题

原始 progressive 方案通常会预设一组候选剪枝层，例如第 `0、6、12、19、25、31` 层。  
如果每个样本都机械地跑满这些层，会带来两个问题：

- 对于简单样本，很多后续层其实已经没有新的剪枝价值，继续执行只会增加额外开销。
- 对于复杂样本，确实需要保留逐层细化能力，不能简单退化成 one-shot。

因此，我们不能用固定层数一刀切。

### 3.2 新思路

新的层数算法不是先拍脑袋决定“只剪 1 层、3 层还是 6 层”，而是先生成一条完整的稠密剪枝计划，然后自动压缩。

具体做法是：

1. 先按原始 AutoPrune 的逻辑，为所有候选剪枝层生成一条完整的保留数量曲线。
2. 观察这条曲线在哪些层真正发生了变化。
3. 对于后面重复不变、已经进入平台区的层，直接删掉，不再执行。
4. 如果整条曲线压缩后只剩一个真正有效的变化点，它就会自然退化成单层剪枝，而不是人为特判。

### 3.3 这个设计的优点

- 保留了原始 AutoPrune “逐层细化”的思想。
- 对简单样本会自动变成少层剪枝，避免无意义的 patch 开销。
- 对复杂样本仍然保留多层 progressive 的能力。
- 这个设计与具体模型层数弱绑定，迁移到别的模型时更稳。

### 3.4 当前结论

这套层数压缩策略已经在 Mantis 上起效。  
当前主方法 `adaptive_absolute_anchor_elbow_scale1_densecompress` 就使用了这套思路。

在当前正式实验中：

- 平均原始候选剪枝层是 `6` 层。
- 压缩后当前主方法平均真正执行的剪枝层数约为 `4.06` 层。

这说明：

- 多层 progressive 没有被放弃。
- 但也已经不再像早期版本那样，所有样本机械跑满固定层数。

## 4. 新增算法二：预算计算从“固定上下限”走向“可解释自适应”

### 4.1 原始问题

旧版 absolute 预算器的动机其实是合理的：

> 文本信息量 / 平均视觉 token 信息密度

也就是说：

- 文本越复杂，说明任务越难，需要保留更多视觉 token。
- 单个视觉 token 的信息越密集，说明每个视觉 token 更“值钱”，可以保留得更少一些。

这个思路本身是有解释性的。  
但旧实现有一个明显问题：

- 最终预算太依赖人工设定的上下限。
- 看起来像“自适应”，实际上很多样本最后都被卡在同一个上限上。

这会削弱算法的可信度，因为最好预算往往是靠调上下限调出来的。

### 4.2 新思路：absolute + elbow-anchor hybrid

这次我们没有放弃 absolute 的动机，而是在它上面加了一层更自然的“样本锚点”。

新的预算器分成两部分：

1. **absolute 控制器**
   - 继续保留“文本复杂度 / 视觉信息密度”这条解释链。
   - 它的作用不再是直接决定绝对预算，而是给出一个相对控制比例。

2. **elbow 锚点**
   - 先从当前样本的注意力累计分布里找到“收益开始明显变平”的位置。
   - 这个位置代表：对这个样本而言，保留到哪里最自然。

最后预算不再是手工上下限，而是：

- 先用 `elbow` 给出样本自己的预算尺度。
- 再由 `absolute` 控制器对这个尺度做温和放缩。
- 再提供一个统一的全局调节参数 `absolute_budget_scale` 作为迁移到别的模型时的粗调旋钮。

### 4.3 这个设计为什么更合理

- 仍然保留了 absolute 的解释性。
- 不再强依赖手工上下限。
- 每个样本的预算会自然不同。
- 迁移到别的模型时，仍然保留一个可控但不过度强硬的单一旋钮。

### 4.4 当前预算结果

在当前正式主实验中，当前主方法的预算表现为：

- 平均输入序列长度：`1586`
- 平均原始视觉预算：`232.35`
- 平均实际视觉预算：`232.34`
- 最终平均保留总 token：`178`

这里看起来有一个容易误解的地方：

- 为什么平均视觉预算已经到了 `232`，最后保留总 token 却只有 `178`？

原因是：

- `232` 对应的是稠密剪枝计划的层均值。
- `178` 对应的是压缩执行后真正落到最后的总 token 数。

也就是说，预算器已经把样本拉到了“200 多视觉 token”这一档，当前真正还需要优化的是 **schedule 尾部形状**，而不是预算器还被旧的上下限绑死。

## 5. 为什么 VILA 上的实验最终失败

### 5.1 失败不是因为代码完全没跑通

VILA 这条线后期其实已经把很多工程问题解决掉了，例如：

- attention 获取方式从公共输出接口改到了模型内部路径。
- NaN budget 之类的明显 bug 被修掉了。
- 剪枝后信息保护机制比最早版本稳定得多。

也就是说，VILA 的失败并不是“代码根本没实现出来”。

### 5.2 真正的问题是什么

VILA 上最核心的问题，是它属于开放式文本生成任务。  
在这种任务里：

- 端到端时间的最大头往往在 decode，也就是逐 token 生成文本的过程。
- 我们的视觉剪枝主要帮助的是 prefill，也就是模型第一次处理长视觉上下文的过程。

因此，哪怕视觉 token 已经剪掉很多：

- prefill 可能变快了，
- 但 decode 依然是大头，
- 端到端未必能变快。

### 5.3 VILA 上的直接证据

VILA 诊断文档在：
[VILA_AUTOPRUNE_DIAGNOSIS_20260329.md](/home/jarvis/VILA/VILA_AUTOPRUNE_DIAGNOSIS_20260329.md)

里面最关键的证据有两类：

1. **极限剪枝也没有带来端到端收益**
   - 第一层后把视觉 token 压得很狠，端到端仍然没有赢 baseline。

2. **固定 decode 长度后，纯计算收益也很小**
   - 说明即便不考虑回答变长，视觉 token 剪枝对这类开放式生成模型的理论端到端收益也有限。

### 5.4 为什么这条线最后不适合当主结果

总结成一句话就是：

> VILA 这类开放式视觉语言模型，推理时间主要消耗在生成阶段，而不是我们剪掉的那部分视觉 token 上。

所以 VILA 更适合作为：

- 失败案例
- 边界条件验证
- 说明“视觉剪枝不是对所有模型形态都天然有效”

而不适合作为当前工作拿正结果的主实验平台。

## 6. 为什么 Mantis 上能做出成功结果

### 6.1 任务定义更匹配

Mantis 这条线最终采用的是：

- `BLINK / Multi-view_Reasoning`
- `ablation1` baseline
- `loss-batched` 主协议

这个任务的特点是：

- 仍然是多视角推理
- 但答案空间更受控
- 不再是自由生成长文本

因此，我们终于能够在同一个 benchmark 上稳定比较：

- 准确率
- 端到端延迟

### 6.2 当前正式主结果

当前正式实验目录：
[20260331_blink_ablation1_accuracy_control_absolute_anchor_main](/home/jarvis/Mantis/runs/autoprune/blink/20260331_blink_ablation1_accuracy_control_absolute_anchor_main)

主结果如下：

| 方法 | 准确率 | 平均延迟 | 相对基线速度 |
|---|---:|---:|---:|
| `baseline_raw` | `55.64%` | `623.23 ms` | `1.00x` |
| `baseline_input_control` | `55.64%` | `623.97 ms` | `1.00x` |
| `fixed48_reference` | `49.62%` | `348.17 ms` | `1.79x` |
| `adaptive_absolute_anchor_elbow_scale1_densecompress` | `55.64%` | `392.92 ms` | `1.59x` |

### 6.3 这组结果说明了什么

这组结果最重要的地方有三点：

1. `baseline_input_control` 与 `baseline_raw` 几乎一致  
   说明我们新增的轻量控制组没有把 baseline 自己拖慢。

2. 当前主方法在**不掉准确率**的情况下显著加速  
   - `623.23 ms -> 392.92 ms`
   - 净减少 `230.31 ms`

3. `fixed48_reference` 更快，但准确率更低  
   它可以作为速度上限参考，但不适合作为最终主方法。

因此，目前最合理的主结论是：

> 当前自适应剪枝方法已经能在 Mantis 的多视角任务上实现“准确率不掉、延迟显著下降”的结果。

## 7. 我们算法自身花了多少时间

### 7.1 当前主实验中的算法开销

| 方法 | 算法额外开销 | 总 patch 时间 | 平均剪枝层数 |
|---|---:|---:|---:|
| `fixed48_reference` | `16.76 ms` | `41.61 ms` | `1.00` |
| `adaptive_absolute_anchor_elbow_scale1_densecompress` | `62.00 ms` | `91.76 ms` | `4.06` |

这说明：

- 单层参考方法的算法税比较小。
- 当前主方法真正额外花时间的原因，是多层 progressive 本身。

### 7.2 当前主方法内部的主要时间桶

当前主方法内部开销大致分成：

- `layout`：`37.64 ms`
- `rank`：`11.34 ms`
- `probe`：`3.01 ms`
- `budget_schedule`：`2.15 ms`

这里最值得注意的是：

- **预算器本身并不贵**
- 当前真正重的是：
  - 布局恢复
  - 有效秩计算
  - 多层执行时的重复物理压缩

这意味着后续优化方向已经很明确：

> 不是继续大幅改预算逻辑，而是继续压缩 progressive 执行的系统开销。

## 8. 剪枝真正省下了多少推理时间

这是这轮实验里最重要的一笔账。

我们把时间拆成三部分：

1. baseline 到当前方法的净端到端降时
2. 当前方法自己的算法税
3. 两者相加，得到“剪枝真正省下来的协议级推理时间”

### 8.1 对账表

| 方法 | 端到端延迟 | 相对 baseline 的净降时 | 算法税 | 剪枝真正省下来的推理时间 |
|---|---:|---:|---:|---:|
| `baseline_raw` | `623.23 ms` | `0.00 ms` | `0.00 ms` | `0.00 ms` |
| `fixed48_reference` | `348.17 ms` | `275.06 ms` | `16.76 ms` | `291.82 ms` |
| `adaptive_absolute_anchor_elbow_scale1_densecompress` | `392.92 ms` | `230.31 ms` | `62.00 ms` | `292.31 ms` |

### 8.2 这张表最关键的含义

这张表说明了一件非常重要的事：

- 当前主方法并没有少省推理时间。
- 它和 `fixed48_reference` 实际上省下来的推理时间几乎一样。

具体来说：

- `fixed48_reference` 省下了 `291.82 ms`
- 当前主方法省下了 `292.31 ms`

二者几乎等价。

那为什么当前主方法反而更慢一点？

答案也很清楚：

- `fixed48_reference` 的算法税只有 `16.76 ms`
- 当前主方法的算法税是 `62.00 ms`

也就是说：

> 当前主方法输给更激进参考组的地方，不在“省推理时间的能力”，而在“自己为了做多层 progressive 额外花的那笔钱”。

## 9. 为什么之前只看到省不到 100ms，现在端到端却能少 200ms 以上

这个问题很容易让人困惑，但本质上是**测量口径不同**。

### 9.1 旧的 `100ms` 是什么

之前那组 `193.08 ms -> 95.50 ms` 的数字，来自历史诊断：

[20260330_ablation1_prefill_breakdown_full133/summary.json](/home/jarvis/Mantis/runs/autoprune/diagnostics/20260330_ablation1_prefill_breakdown_full133/summary.json)

它测的是：

- 单次 prompt-only
- 只看模型本体
- 只看 prefill

所以它回答的是：

> 长视觉序列在模型本体里到底值不值钱？

答案是：值，一次前向里大约值 `100 ms`。

### 9.2 当前主协议测的是什么

当前正式主协议不是“单次 prompt-only 前向”，而是：

- `BLINK`
- `loss-batched`
- 对多个候选答案做 batched scoring

因此它测的不是单次 prefill，而是：

> 整套候选答案打分协议的总成本

所以现在主协议里能看到：

- `230 ms+` 的净端到端降时
- `292 ms+` 的协议级推理时间节省

这并不是和旧诊断矛盾，而是：

- 旧诊断只看了一次单前向
- 当前主协议看的是整套评测流程

## 10. 当前阶段最值得保留的结论

### 10.1 关于算法

- 剪枝层数自适应压缩是必要的。
- 预算器保留 absolute 动机是合理的。
- `absolute + elbow-anchor` 是比旧版固定上下限更稳的方向。

### 10.2 关于 VILA

- VILA 的失败不是简单工程 bug。
- 更主要的原因是模型形态与任务形态不匹配。
- 它适合作为失败边界案例，不适合再作为当前主正结果平台。

### 10.3 关于 Mantis

- Mantis 上已经得到了当前最完整、最可信的正结果。
- 当前主方法可以做到：
  - 准确率不掉
  - 延迟显著下降
- 当前最大的剩余问题，不是预算器，而是 progressive 的系统执行成本。

## 11. 下一步建议

接下来最值得做的，不是再去大幅折腾 benchmark，也不是重新回到手工上下限，而是继续做两件事：

1. 保留当前 `absolute + elbow-anchor` 预算器主线。
2. 重点优化 progressive 的执行方式：
   - 减少布局恢复开销
   - 减少有效秩计算开销
   - 减少中间层重复物理压缩次数

一句话总结当前阶段：

> 预算问题已经基本解决，主结果已经成立，下一阶段真正的优化重点是执行效率，而不是再去重建算法动机。
